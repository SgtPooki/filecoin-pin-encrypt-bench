Encrypt the CAR

Benchmarking three payload formats for password-protected uploads: raw bytes, tar, and a UnixFS CAR. 30 round trips, 400 random reads, 5 hours of 4K video played in Chrome, one upstream bug.

All numbers measured at runtime on an Apple Silicon Mac (10 cores, 64 GiB), Node 24.18, Kubo 0.43.1 offline, Chrome via Playwright 1.60. Code and raw JSON: bench/pkg.

the questionWhat goes inside the envelope is forever

The Filecoin Encryption Envelope (FEE) wraps plaintext in chunked AES-256-GCM. It does not care what the plaintext is, and its only header slot (appMetadata) is public.

filecoin-pin PR #771 encrypts the raw file bytes. A reviewer proposed a UnixFS CAR instead. A third reviewer proposed tar.

Uploads to Filecoin are immutable and paid. Whatever ships first, every decryptor has to read it for as long as the data exists.

the idea everything rides onMetadata-first block order makes a CAR seekable with no index

A CARv1 is just a header followed by blocks. Writers normally emit leaves first and the root last, so a reader cannot locate anything until it has read everything.

Rule: write every dag-pb node first (breadth-first from the root, each once), then every raw leaf in file order, each CID once.

A reader streams from offset 0 until the DAG closes, cancels, and from then on every file offset is arithmetic.

offset(leafk) = header + Σ metadata sections + Σj<k (varint + 36 B CID + Tsizej)

Kubo imports the result as ordinary UnixFS (dag import, ls, gateway fetches byte-identical). The order only matters to readers that want to seek without an index; built in two passes over the input, no plaintext temp file.

the surpriseEvery add of a 2 to 4 GiB file produces a root Kubo cannot parse

The first 4 GB video (3,891,799,298 bytes) failed for all three formats at the outer-CAR stage: 500 proto: cannot parse invalid wire-format data. Not a payload issue: the outer object is built by filecoin-pin's own packer.

protons-runtime stores the low word of a uint64 as lo | 0. For values in [2^31, 2^32) it goes negative, 5 bytes are reserved, writeVarint64 writes one, and 4 bytes of allocUnsafe garbage follow. UnixFS filesize and blocksizes are uint64.

blockSizes: [2147483647n] → 080218ffffffff07... ok
blockSizes: [2147483648n] → 0802180000000000... bad
blockSizes: [4294967296n] → 080218808080801020... ok
status
filecoin-pin #773 filed
Reproduced with the PR worktree's own ipfs-unixfs 12.0.2 and independently confirmed by a Codex (gpt-6-astra) investigation with a differential test: 5,008 of 20,007 sampled values corrupt, all in the window. Upstream fix is one line. The 5 GiB input passed because its subtrees are 1 GiB and its total is above 2^32.

recommendationPin one profile: UnixFS CAR, wrapped, metadata-first

  • Container: CARv1, one root, content_type: application/vnd.ipld.car; decryptors reject anything else. A future change gets a new content type.
  • Root: anonymous UnixFS directory with exactly one child named basename(input), file or directory, so add dir/ keeps its name.
  • DAG: the unixfs-v1-2025 profile the repo already pins; inner CIDs equal an unencrypted add.
  • Order: dag-pb nodes first (BFS, each once), then raw leaves in file order, each CID once.
  • appMetadata: unchanged (kdf, iterations, salt). Nothing about the plaintext in the public header.
  • Encrypt: two passes, no plaintext temp file, re-hash leaves in pass 2 and abort if the input changed, stream into fee.encrypt. Symlinks skipped and reported.
  • decrypt <file> <outDir>: create outDir 0700, write the wrapper's children (0600, exclusive), path-jailed, remove on failure. No single-file special case.
  • Viewer: Range-fetch the envelope, read the metadata prefix once, serve files by span with one decryptRange per contiguous run of leaves. Never buffer the plaintext CAR.
  • Piece metadata: name stays encrypted.fee; outer object unchanged.

Accepted cost: about 2x CPU on add and on decrypt. Matched: raw and tar's seek parity (coalesced reader). Gained: names, directories, HAMT, dedup, plaintext CIDs, one viewer path for encrypted and unencrypted roots.
