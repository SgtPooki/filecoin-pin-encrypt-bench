**Adopt CAR-in-envelope now, before the first encrypted release**, provided initial browser support can require downloading before viewing. Bundles are already a requirement. Shipping raw first buys simpler extraction and better media seeking, but creates a lasting compatibility branch when bundles arrive. If immediate playback of ~1 GiB videos is mandatory, resolve that architecture before release; CAR wrapping alone does not deliver it.

1. **Browser memory and range playback are the main cost.** Chunked WebCrypto can bound cryptographic memory, but cannot fix unordered UnixFS blocks. A naive ciphertext → plaintext CAR → blockstore → output Blob pipeline can retain several file-sized allocations. The [existing browser backend](/Users/sgtpooki/code/work/filoz/filecoin-project/filecoin-pin-decrypt/src/core/car/car-memory-backend.ts:75) concatenates accumulated chunks. Use disk-backed staging plus an index, handle quota failures and cleanup, and test target browsers. Raw payload offsets map directly through FEE; inner file offsets require UnixFS traversal and CAR block locations. DFS helps sequential reads, but deduplicated blocks and seeking still require caching/indexing. CARv1 supplies no index. [CAR specification](https://ipld.io/specs/transport/car/carv1/#performance)

2. **Privacy improves usability, not size concealment.** CAR preserves encrypted filenames, hierarchy and inner CIDs; raw currently discards names. Neither hides total envelope length or public KDF parameters. CAR overhead/deduplication changes size leakage without providing padding. Keep filenames, original MIME types and plaintext CIDs out of public headers and piece metadata. A public CAR media type reveals only the container choice. Both formats permit offline password guessing; generated share passwords should have high entropy. Decrypted HTML also needs isolation from the viewer’s trusted origin.

3. **Implementation exceeds “unpack a CAR.”** Existing dependencies help, but declare the exporter directly if importing it. Add packing, indexing, safe extraction and browser file routing. The current builder writes plaintext CARs into the system temp directory using [default permissions](/Users/sgtpooki/code/work/filoz/filecoin-project/filecoin-pin-decrypt/src/core/car/car-file-backend.ts:44), without guaranteed cleanup across construction failures: use private staging. Budget additional disk passes and archive storage. Preserve exclusive creation, restrictive permissions and failure cleanup for directory extraction. The single-file builder rejects CAR inputs, although encrypted uploads currently allow them; preserve those as ordinary file bytes. Scope wrapper support to encryption.

4. **Alternatives solve narrower problems.** An encrypted filename prefix/manifest plus raw bytes preserves calculable media offsets, but creates a custom container and still needs bundle semantics. Uncompressed tar offers sequential extraction and familiar tooling, but needs scanning/indexing for seeking and adds another ecosystem. CAR fits this project’s UnixFS model; generic FEE tools recover the CAR, while application-aware tools restore files. Reordering CAR blocks later can remain compatible if readers accept arbitrary order; it cannot improve existing archives.

5. **Specify the profile before release.** Require CARv1, one root, a complete supported UnixFS DAG, and a synthetic wrapper containing exactly one entry named after the input, whether file or directory. Define empty directories, hidden-file selection, Unicode/case collisions, symlinks and metadata preservation. Make CLI output a new extraction directory; restore the child unchanged. Viewer: open a sole file, otherwise list the directory; specify any `index.html` convention. Reject unsafe paths and enforce extraction limits. Set `content_type` to `application/vnd.ipld.car` and add a namespaced profile/version beside KDF metadata; never sniff to choose raw versus CAR. Specify KDF/password encoding, supported codecs and unknown-version rejection. Allow optional future metadata. Include cross-runtime fixtures and truncated/corrupt-archive tests. No specification can promise “never another format,” but this removes today’s foreseeable migration.
